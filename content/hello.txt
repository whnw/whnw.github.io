• 下面是几个典型场景。

  ### 例 1：新增的普通 bool 配置项

  config FEATURE_FOO
      bool "Enable foo feature"

  旧 .config 中没有 CONFIG_FEATURE_FOO。由于该选项可见、没有用户值且可以修改，会触发：

  *
  * Restart config...
  *
  * Reason: CONFIG_FEATURE_FOO is visible but has no user value
  *   prompt: Enable foo feature
  *   type: boolean; restart condition: symbol is changeable
  Enable foo feature (FEATURE_FOO) [N/y/?]

  这是最常见的情况：代码更新后新增了 Kconfig 选项，但旧配置文件里没有它。

  ### 例 2：依赖条件刚刚变为可见

  config NETWORKING
      bool "Networking support"

  config FEATURE_HTTP
      bool "HTTP support"
      depends on NETWORKING

  原来：

  CONFIG_NETWORKING=n

  此时 FEATURE_HTTP 不可见，不会触发。

  如果配置过程中将 NETWORKING 改为 y，而 .config 中没有 CONFIG_FEATURE_HTTP，下一次扫描就会发
  现它已经可见且没有用户值：

  * Reason: CONFIG_FEATURE_HTTP is visible but has no user value
  *   prompt: HTTP support
  *   type: boolean; restart condition: symbol is changeable

  也就是说，修改一个上层选项可能让新的下层选项出现，从而需要重新进入配置。

  ### 例 3：新增的字符串或整数配置

  config HTTP_PORT
      int "Default HTTP port"
      depends on FEATURE_HTTP

  当 FEATURE_HTTP=y，但旧配置中没有 CONFIG_HTTP_PORT 时：

  * Reason: CONFIG_HTTP_PORT is visible but has no user value
  *   prompt: Default HTTP port
  *   type: integer; restart condition: symbol is changeable
  Default HTTP port (HTTP_PORT) [0]

  字符串、十六进制和整数配置也适用同样的判断，并不限于 bool。

  ### 例 4：启用的 choice 没有选中项

  choice
      prompt "Select compression method"
      default COMPRESS_GZIP

  config COMPRESS_GZIP
      bool "gzip"

  config COMPRESS_LZMA
      bool "lzma"

  endchoice

  如果这个 choice 当前处于启用状态，但配置里没有有效的选中项，会触发：

  * Reason: <anonymous choice> is visible but has no user value
  *   prompt: Select compression method
  *   type: boolean; restart condition: enabled choice has no selected value

  随后会要求选择：

  Select compression method
    1. gzip
    2. lzma
  choice[1-2?]:

  这里显示 <anonymous choice>，因为 Kconfig 的 choice 本身通常没有符号名。

  ### 例 5：有默认值，但没有用户值

  config FEATURE_BAR
      bool "Enable bar"
      default y

  即使计算后的默认值是 y，也不一定代表它已经有用户配置值。若 sym_has_value(sym) 仍为假，而且
  选项可修改，仍可能触发：

  * Reason: CONFIG_FEATURE_BAR is visible but has no user value
  *   prompt: Enable bar
  *   type: boolean; restart condition: symbol is changeable

  这里“没有用户值”指配置文件或配置过程中没有明确记录用户选择，不等同于“计算后的当前值为空”。

  ### 不会触发的反例

  以下情况不会出现 Restart config...：

  - 配置项由于 depends on 不满足而不可见。
  - .config 中已经存在该配置项的用户值。
  - 配置项虽然没有用户值，但当前不可修改。
  - 菜单节点没有关联 symbol，例如纯菜单或注释。
  - choice 没有用户值，但当前并未启用。



• 推荐执行：

  yes '' | make oldconfig

  它会：

  - 保留 .config 中已有配置
  - 对新增或缺失的可见选项采用默认值
  - 自动处理依赖变化后新出现的选项
  - 最终将完整、收敛后的配置重新写入 .config

  如果希望手动决定新增选项，则执行：

  make oldconfig

  每个新增选项都会提示选择；直接按 Enter 使用默认值。

  更新完成后，可以再验证一次：

  make silentoldconfig

  此时不应该再出现 Restart config...。如果仍然出现，新增的原因输出会指出具体是哪个符号。

  建议更新前备份：

  cp .config .config.backup
  yes '' | make oldconfig

  需要注意，“包含所有选项”实际指包含当前 Kconfig 条件下所有需要记录的选项。由于 depends on 不
  满足而不可见的选项，可能不会写入 .config；以后依赖变为满足时，仍可能作为新选项出现。

  如果不需要保留当前配置，也可以完全重新生成：

  make defconfig       # 全部采用 BusyBox 默认配置
  make allnoconfig     # 尽可能全部关闭
  make allyesconfig    # 尽可能全部启用

  对于保留现有配置并避免后续触发 restart，首选：

  yes '' | make oldconfig

› 能否执行no '' | make oldconfig


• 不可以，通常不存在 no 这个命令：

  no '' | make oldconfig

  一般会报：

  zsh: command not found: no

  如果想持续输入 n，语法是：

  yes n | make oldconfig

  但不推荐：遇到整数、字符串或 choice 选项时，n 可能是无效输入，导致反复询问甚至死循环。

  更安全的选择：

  yes '' | make oldconfig

  它会对缺失选项使用各自默认值。若想把所有能够关闭的选项设为 n，使用：

  make allnoconfig

  不过 allnoconfig 会重建整个 .config，不会保留当前已有的启用配置。


如果希望 Codex 和各种 Copilot 场景都尽量稳定遵守，推荐使用两个入口：

  your-repository/
  ├── AGENTS.md
  └── .github/
      └── copilot-instructions.md

  其中：

  - AGENTS.md 保存完整规范，供 Codex及支持 Agent instructions 的 Copilot 使用。
  - .github/copilot-instructions.md 保存相同规范，或明确要求读取仓库根目录的 AGENTS.md。这是
    Copilot 官方的仓库级指令路径。GitHub 官方配置说明


  可以复制现有规范：

  mkdir -p ~/.copilot
  cp AGENTS.md ~/.copilot/copilot-instructions.md

  Copilot CLI 还支持拆分形式：

  ~/.copilot/instructions/**/*.instructions.md

  官方说明见 Copilot CLI 自定义指令
  (https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-custom-instructions)。

  需要注意：

  - ~/.copilot/copilot-instructions.md：对本机 Copilot CLI 的所有项目生效。
  - VS Code、Visual Studio、GitHub.com Copilot 不保证读取该用户目录文件。
  - IDE 和云端 Copilot 最稳妥的方式仍是在每个仓库放置 .github/copilot-instructions.md
    或受支持场景下的根目录 AGENTS.md。各客户端支持范围







根因是：Copilot CLI 在 Ubuntu 中运行，但颜色最终由 Windows Terminal 渲染。你只把背景改成白色，而 Copilot 仍使用深色配色，因此部分函数名、变量名继续输出白色。

建议按以下顺序处理。

1. 更新 Ubuntu 中的 Copilot CLI

这是远程 Ubuntu 里的版本，不是 Windows 或 macOS 中的版本：

copilot version
copilot update

如果通过 npm 安装：

npm install -g @github/copilot@latest

新版改进了 GitHub 主题对浅色终端的适配。

2. 固定使用 GitHub 主题

进入 Copilot 后执行：

/theme github

如果该命令没有直接生效，执行：

/theme

然后在界面里选择 github。也可以使用：

/settings theme github

主题会保存在远程 Ubuntu 的：

~/.copilot/settings.json

可以检查：

grep -n '"theme"' ~/.copilot/settings.json

应该类似：

{
  "theme": "github"
}

当前官方支持的主题包括 default、github、dim、high-contrast 和 colorblind；其中新版 github 主题能够针对浅色终端使用 GitHub Primer 浅色调色板。官方命令参考 · 配置文件参考

3. 先设置 Windows Terminal，再启动 Copilot

Copilot 启动时会探测终端背景。因此应按这个顺序：

Windows Terminal 选择完整的 OneDark Light 配色方案。
关闭当前 Copilot。
最好重新打开一个 Windows Terminal 标签页。
SSH 登录 Ubuntu。
再运行 copilot。

不要在 Copilot 已经启动之后单独修改背景色，因为它可能不会重新计算配色。

4. 检查 SSH 终端能力

在 Ubuntu 中运行：

echo "$TERM"
tput colors

推荐结果：

xterm-256color
256

如果 $TERM 是 dumb、vt100，或者颜色数只有 8，可临时测试：

TERM=xterm-256color copilot

如果这样显示正常，再加入 Ubuntu 的 ~/.bashrc：

export TERM=xterm-256color

不过如果当前已经是 xterm-256color，就不要重复设置。

5. 最稳妥的无彩色方案

如果 GitHub 主题仍有个别白字，这是 Copilot CLI 已报告过的浅色主题兼容问题。可以完全禁用 ANSI 颜色：

NO_COLOR=1 copilot

确认显示正常后，在 Ubuntu 的 ~/.bashrc 中添加：

copilot-light() {
    NO_COLOR=1 command copilot "$@"
}

以后运行：

copilot-light

这种方式会失去语法高亮，但能保证白底下所有内容可读。建议优先尝试 /theme github，NO_COLOR=1 作为兜底。
